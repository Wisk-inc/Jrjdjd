# CorX Labs site: notes for Claude Code

## House style for everything written here

Pages, release notes, feed items, llms.txt, blog posts and X posts all follow this. Nathan's own voice is short
and direct; the site should read the same way.

- **Short, plain sentences.** Say the thing. Numbers beat adjectives.
- **No em dashes in prose.** Use a comma, a colon, a full stop or brackets. Page titles keep the
  "Name — subtitle" form.
- **Don't praise the writing.** No "stated plainly", "honest about", "we say so plainly", "the honest answer".
  State the limit and move on. ("Honest" is fine as a model behaviour, e.g. CorX3.8's register.)
- **No "not just X, but Y"** and no "It's not X, it's Y".
- **Avoid these words:** delve, tapestry, testament, pivotal, underscore, showcase, seamless, robust, landscape,
  realm, crucial, vibrant, foster, enhance, meticulous, boast, groundbreaking, renowned, additionally,
  moreover, furthermore, "in summary", "it is important to note".
- **No trailing "-ing" clauses** that add significance ("…, highlighting how…").
- **Bold sparingly**, headings in sentence case.
- **Every claim from the project's own docs or benchmark files**, with losses next to wins.

Run `python3 tools/style-check.py` before committing; it lists what to fix.

## Release workflow

- Work on the session's `claude/...` branch, then merge into `main` with `git merge --no-ff` and push.
- Page titles don't change.
- The site's address is `https://www.corx-labs.com` (Vercel redirects `corx-labs.com` there). Every absolute link
  in a page, the sitemap, llms.txt and feed links use www. Feed `<guid>` values stay as first published.
- FAQ answers must match their FAQPage JSON-LD text exactly.
- Check pages in a browser under the CSP in `_headers`, at 360, 390 and 1440 px, in light and dark.
- `models/pluvium/index.html` is generated: edit `tools/build-pluvium-page.py` and `tools/pluvium_scorecard.py`,
  then run `python3 tools/build-pluvium-page.py`. Benchmark pages come from `tools/build-benchmarks.py`.
- `scam-radar/index.html` is generated by `tools/build-scam-radar-page.py`, which writes real numbers into it from
  `assets/data/scam-radar.json`: refresh that copy from the `scam-radar-data` branch before building. The data is
  published by `.github/workflows/scam-radar.yml`: it scans around the clock in one-minute cycles and publishes after
  every cycle; each 55-minute run starts the next, and `scam-radar-keepalive.yml` restarts the chain if it stops.
  GitHub's own schedule skips most starts, so it is only the backstop. The status file says whether a scan is
  running (`scan.state`), and the snapshot keeps the last cycles (`recentCycles`) for the page's live chart.
  raw.githubusercontent.com can serve a branch's old files for minutes after a push, so the page and the map
  ask `api/scam-radar-status.js` for the branch's current commit and read files at that commit.
- `.github/workflows/site-check.yml` (manual) checks the live site from a GitHub runner: host, which commit
  each live file matches, the APK, redirects, CSP, scan API, Radar data age, and the pages in a real browser.
  This sandbox cannot reach the site; run that workflow and read its log instead.
- What may be published is decided in `tools/scam-radar/sanitize.mjs` and `export.mjs`: a site is named only on
  strong evidence, defanged, and from a scam page only its title is kept, with phone numbers, emails and links
  removed. Never contacts, tracking IDs, page text or code. Contacts from named sites go out only as slow one-way
  keys (`contacts/xx.json`, PBKDF2-SHA256 with a million rounds, cached in `contact-keys.json` next to the database)
  so the page can match one a visitor pastes. A fast hash would let anyone hash every number in a country and
  get the list back. Jamaican numbers are counted, never listed. A real site hacked to host a scam page (domain registered a year or more
  before Radar first saw it, no borrowed brand in its name, not a hosting platform) is counted, never named.
- Each scan run starts `tools/scam-radar/hunt-jamaica.mjs --hunt` in the background (Scam Finder's `jamaica` and
  `lottery` hunt profiles, about eight minutes). Its leads are added between two cycles with `--add`, so only one
  process writes to Radar's database at a time.
- The link checker's deep dive is `GET /api/scam-finder?depth=2` (up to 40 s; `vercel.json` gives the function
  60 s), three per ten minutes per address. `?contact=` checks an email address or phone number. Breach checks
  need `HIBP_API_KEY` on the host. `api-core.mjs` checks every address the function connects to.
- `scam-radar/map/index.html`, `assets/css/scam-map.css` and `assets/js/scam-map.js` come from
  `python3 tools/build-scam-map-page.py` (Scam Finder's viewer, unedited; this site's changes are in
  `assets/js/scam-map-boot.js`).
- `assets/js/scam-finder-core.js`, `api/scam-finder.js` and `netlify/functions/scam-finder.js` are bundles: after
  changing `tools/scam-radar/`, run `node tools/scam-radar/build-bundles.mjs` (it fetches esbuild through npx).
